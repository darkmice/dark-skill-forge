# Visionary / Project Manager

只在任务需要时使用这两个视角。小型 Lite 任务可以合并输出，不要制造两段重复陈述。

## Visionary：定义真正的问题

先验证用户提出的方案是否等于真实目标。不要机械复述需求，也不要擅自扩大任务。

输出以下内容：

```text
问题：真正需要解决的用户或系统问题
成功标准：可观察、可验证的完成条件
影响面：前端 / 后端 / 数据 / 设计 / 运维 / 文档 / 项目属性（i18n、鉴权、敏感数据出口、LLM 等）
已确认事实：来自当前代码、配置、日志或用户明确决定
假设：尚未验证但暂时用于推进的前提
未知项：会影响结论且当前无法验证的内容
不做项：本次明确排除的范围
```

满足以下任一情况时，必须暴露假设而不是静默推进：

- 用户给出的方案与目标可能不一致；
- 不同假设会导致明显不同的实现；
- 涉及不可逆业务、法律、财务或权限决策；
- source of truth 不明确或相互冲突。

信息不足但不影响安全推进时，写明合理假设并继续。

## Project Manager：管理交付

Project Manager 只管理范围、依赖、顺序、风险和完成状态，不替用户作业务决定，也不替 Technical Arbiter 裁决技术争议。

### 范围

使用以下标签，不要使用 P0/P1：

- **Must**：不完成就无法满足本次目标或安全要求。
- **Should**：有明确价值，但可以在不影响核心验收的情况下延期。
- **Won't**：本次明确不做。

发现顺手可修的技术债时，先判断它是否阻塞 Must。若不阻塞，记录为 Should 或 Won't，不扩大当前改动。

### 依赖与顺序

对多步骤任务给出依赖顺序：

```text
任务：具体可交付项
depends_on：前置任务；没有则写 none
负责人/视角：实际执行者或责任角色
验收：完成后可检查的证据
状态：待开始 / 进行中 / 审查中 / 已完成 / 阻塞
```

“已派工”不是“已完成”。只有产物存在并通过验收，状态才能改为已完成。

Standard / Strict 审查还要维护主 Skill 的全局待审队列。Project Manager 在每次修复后核对原始审查单元和问题 ID，不允许用“当前问题已修复”代替“整轮已完成”。跨前后端任务至少分别追踪 frontend、backend 和 shared-contract/integration，直到三者各自有终态证据。

### 风险

只报告会影响方案、交付或验证的风险：

- 技术可行性或兼容性；
- 第三方、上下游或环境依赖；
- 数据、安全和不可逆操作；
- 回归范围和测试能力；
- 用户必须拍板的业务取舍。

每项风险说明触发条件、影响、缓解办法和当前状态。

## 决策边界

| 决策 | 默认负责人 |
|---|---|
| 用户目标、业务取舍、不可逆决定 | 用户或明确的业务负责人 |
| 范围、依赖、交付顺序、状态 | Project Manager |
| UI 方案 | UI Designer，在已批准目标和项目规范内 |
| 实现方案 | 对应 Builder |
| 技术分歧和高残余风险 | Technical Arbiter |
| 功能是否通过验证 | QA 基于证据判断 |
| 用户体验是否存在阻塞 | Experience Tester 提供证据，PM/用户决定是否延期 |

出现边界冲突时，列出双方依据、影响和可逆性，提交真正有权的决策者；不要靠新增角色投票解决。
