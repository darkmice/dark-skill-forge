# QA Engineer / Technical Arbiter / Experience Tester

这三个视角解决不同问题：

- QA 判断功能和回归是否有证据支持；
- Technical Arbiter 裁决已批准范围内的重大技术分歧；
- Experience Tester 判断真实用户流程是否可理解、流畅且可恢复。

它们都不能替代用户作业务、财务、法律或不可逆决策。

## QA Engineer

从验收标准反推测试，不机械追求固定测试数量。

### 执行时机

QA 在阶段开始时设计验证矩阵，在 Dark Tribunal 审核期间检查测试盲区和 oracle，但不为每个文件、问题或小修复反复运行 test、check、lint、typecheck、build 或 E2E。只有本阶段实现、两轮差异化审查、集中修复和必要关闭轮全部结束后，才由主 Skill 的 `stage-validation` 单元统一执行验证矩阵。

- 阶段是预先定义的可独立交付纵向切片或用户里程碑，不是单个问题或一次保存；
- 可安全并行且互不污染的检查可以在阶段末并行，同一观察范围只运行一次；
- 审核前只允许阻塞性最小诊断，必须标记 `diagnostic-only`，不能作为通过证据；
- 集中验证失败时先汇总失败并批量修复，完成对应关闭审查后，再重跑失败项和受影响回归；不要每修一个失败就重跑全套；
- 用户明确要求 TDD、项目硬性门禁要求更早执行或安全 Blocker 需要即时隔离证据时，按主 Skill 的例外规则处理并记录偏离原因。

### 测试覆盖

根据改动选择适用场景：

- 主要成功路径；
- 错误、超时、取消和恢复；
- 空值、极值、重复操作和并发；
- 权限、租户和身份边界；
- 新旧数据、客户端或接口兼容性；
- 项目存在 i18n 时，至少两个差异明显的 locale、missing key/fallback，以及适用的 RTL、文本膨胀、语言切换或 SSR hydration；
- 命中敏感数据或外部出口时，使用合成 canary 验证响应、日志/trace、第三方请求、导出、缓存/向量写入和异常路径不泄露原值；
- LLM/RAG/Agent 命中时，验证模型输入输出、streaming、prompt injection、跨租户检索、工具参数和副作用 sink，而不只断言 prompt 模板；
- 受影响的既有回归路径。

优先复用仓库已有测试入口。高风险结论需要更接近真实环境的证据；静态检查不能替代运行验证，单元测试也不能自动替代端到端路径。

### 测试观察边界

在把测试结果作为通过证据前，记录：

- 测试入口、fixture 和数据来源；
- 断言实际观察的层级、字段与副作用；
- 未覆盖的调用形态、消费者、环境和失败路径；
- 测试 oracle 是否能识别漏映射、错映射、静默降级或部分成功。
- i18n 测试实际观察的是 key 集合、最终文案、locale-aware 格式、路由/持久化还是布局；默认 locale 通过不得外推到其他 locale。

审核阶段发现盲区后，先把人工调用链、静态查询、定向测试或真实操作登记进阶段验证矩阵；审核关闭后集中执行。测试通过只说明其观察范围内通过，不得外推成影响面完整。

### QA 报告

```text
### QA 验证报告

范围：实际验证的功能、模块和环境
验收条件：
- [条件] → 通过 / 失败 / 未验证；证据：命令、日志或操作结果

新增或回归场景：
- [场景] → 结果

发现：
- 按统一发现格式列出；没有则写“未发现问题”

未验证与残余风险：
- 原因、影响和建议下一步
```

不得把“计划运行”“测试已启动”或“预期会通过”写成通过。

是否允许写入严格遵循主 skill 的“默认修复协议”。获得写入授权后，QA 发现范围内缺陷时把同批失败证据统一交回对应 Builder；Builder 集中修复、Dark Tribunal 完成关闭审查后，再重跑失败场景及受影响回归。不要把“是否修复”作为用户确认点，也不要在每个小修复后重跑全套。

## Technical Arbiter

仅在 Strict 模式、重大技术分歧、架构边界冲突或高残余风险时启用。普通实现细节由 Builder 按项目规范决定，不需要额外裁决仪式。

裁决前：

- 确认问题仍在已批准范围内；
- 列出候选方案及各自证据；
- 比较正确性、安全、可逆性、兼容性、复杂度和长期成本；
- 区分事实、假设与价值判断；
- 确认是否存在必须由用户决定的业务取舍。

输出：

```text
裁决：选择的方案或暂不裁决
依据：决定性证据和约束
放弃方案：为什么不选
风险：仍然存在的风险及缓解方式
复核条件：什么新事实出现时需要重审
```

Arbiter 不管理排期和人员，不重新定义用户目标，也不把个人偏好包装成技术必然。

## Experience Tester

只在存在用户可见流程且环境允许真实操作时启用。必须实际使用功能，不能通过阅读代码或 QA 报告假装完成体验验证。

走查至少关注：

- 首次进入时能否理解下一步；
- 主要任务需要多少决策和操作；
- loading、成功、失败和空状态反馈是否及时；
- 错误后能否恢复，危险操作是否可撤销或确认；
- 键盘、触摸、不同视口和辅助技术是否存在明显障碍；
- 文案、信息层级和操作结果是否一致。

竞品对比不是默认必做。只有存在明确比较目标和可验证材料时才使用。

### 体验报告

```text
### 体验方报告

环境：设备、视口、版本及必要配置
使用路径：实际完成的操作
顺畅点：有保留价值的行为
卡点：位置、触发条件和用户影响
建议：按影响排序的最小改进
未覆盖：无法操作或尚未验证的场景
```

体验缺陷使用统一严重度，不另建一套 P0/P1。是否延期由 PM、用户或明确的业务负责人结合影响和发布目标决定。

## 最终门槛

交付前确认：

- 所有 Must 验收条件均有证据；
- Blocker 已清零，High 已修复或明确接受风险；
- 代码修复经过复审；
- 除只读或明确阻塞项外，已确认缺陷已直接修复并重验；
- Standard / Strict 已完成至少两轮差异化审查；第二轮若修改任何任务产物或工作区文件，关闭轮已经完成；
- 阶段末集中验证只在审核候选关闭后执行；没有把单文件、单问题或单次保存伪装成阶段，也没有无理由重复运行同一检查批次；
- 每轮全局待审队列已按 ID 和表面对账，没有被单项修复覆盖的 frontend、backend、shared-contract/integration 或问题项；
- security/data-egress 单元在适用时已两轮销账；真实出口 canary、注入边界和 LLM 专项没有被普通功能测试替代；
- QA 只对实际执行的验证负责；
- 体验方只对实际走查的路径负责；
- 未验证内容、环境限制和残余风险已披露。

若这些条件不满足，明确报告“未完成”或“验证不足”，不要用角色共识替代证据。
