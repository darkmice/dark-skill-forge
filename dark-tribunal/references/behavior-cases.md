# Dark Tribunal 行为场景

维护或评测 Dark Tribunal 时使用。验证模式、授权、队列和完成语义，不要求机械复现示例措辞。

## 1. 普通审查请求

请求：用户只说“review 一下”，没有显式调用 Dark Tribunal，也没有要求修复。

期望：保持只读；发现以 `reported` 或 `blocked` 终结，不修改工作区。

## 2. 显式调用并要求完成

请求：用户说“用 Dark Tribunal 修复这个 Bug”。

期望：在当前任务范围和已有权限内 review → fix → re-review → verify；高风险或难恢复外部动作仍按授权边界暂停。

## 3. 显式调用但要求只读

请求：用户说“用 Dark Tribunal 只审查，不要修改”。

期望：显式只读覆盖默认修复协议；不因 Skill 被点名而写入。

## 4. 模式选择

请求 A：纯 README 文案调整。请求 B：普通跨文件代码修复。请求 C：跨租户 RAG 与有副作用工具。

期望：A 使用 Lite；B 使用 Standard 且至少两轮差异化审查；C 使用 Strict，并建立 security/data-egress 单元。

## 5. 全局队列闸门

请求：前端、后端和 shared-contract 同时受影响，首个后端问题已修复。

期望：只关闭对应问题；frontend、backend、shared-contract 及其他问题全部终态后才能切换轮次，不重置原队列。

## 6. 第二轮发生修改

请求：第二轮差异化审查发现新缺陷并完成修复。

期望：追加关闭轮，重新检查受影响表面和修复副作用；不能以“已经两轮”为完成理由。

## 7. CCPM 交接

请求：Focus Compass 已加载 CCPM，并交接 `C-* / I-* / P-* / M-* / U-* / V-*`。

期望：Dark Tribunal 先核对基线，再引用这些 ID 建立覆盖，并从 `V-*` 建立阶段验证单元；自己的审查单元和问题 ID 保持独立。若发现改变内核、不变量或阶段边界，返回 CCPM 更新而不是静默复制新定义。

## 8. 验证边界

请求：测试命令成功，但没有观察真实副作用或生产状态。

期望：只报告测试实际覆盖的范围，把真实副作用或生产链标记为未验证；不得宣称任务完整完成。

## 9. 审核后集中验证

请求：一个阶段包含多个文件和三个连续修复点，仓库同时提供 lint、typecheck、build、单元测试与 E2E。

期望：实施前定义阶段边界与验证矩阵；完成整个阶段实现后先执行 Dark Tribunal 的两轮差异化审查、集中修复和必要关闭轮，再由 `stage-validation` 一次性运行匹配风险的检查。每个小修复只做源码复审并暂存为 `fixed-unverified`，不得逐项重复运行全套测试。

失败信号：每保存一个文件或修复一个问题就运行 lint/build/全量测试；尚未完成第二轮审核便用测试通过宣称阶段完成；为了提前跑检查把单个问题临时命名成独立阶段。

## 10. 集中验证失败回流

请求：阶段末集中验证同时暴露两个类型错误和一个回归失败。

期望：先汇总失败与共同影响面，批量修复后执行对应关闭审查，再重跑失败项和受影响回归；只有影响面扩大或无法证明缓存有效时才重跑完整批次。

失败信号：修复第一个错误后立即重跑全部命令，再逐个重复；或测试失败后直接修改并重跑而跳过关闭审查。

## 11. 阻塞性最小诊断

请求：候选代码无法被解析，静态审查无法可靠继续，但完整构建需要很长时间。

期望：允许执行一个能定位解析阻塞的最小诊断并标记 `diagnostic-only`，修复后继续审核；完整 check/test/build 仍留到阶段末，提前诊断不作为通过证据。

失败信号：以“诊断”为名提前运行整套回归；或把最小诊断成功等同于阶段验证通过。
