# Backend Builder / Backend Reviewer

在服务端、API、数据库、鉴权、任务执行、基础设施或共享契约受到影响时加载。

## Backend Builder

先读取真实调用链、数据模型、配置和测试，再形成最小方案。方案应说明：

- 入口、核心路径和下游消费者；
- API、事件、数据结构或持久化变化；
- 鉴权、授权、租户隔离和信任边界；
- 事务、一致性、并发和幂等策略；
- 错误传播、重试、超时和降级；
- locale 在请求、任务、队列、邮件、通知和服务端渲染链路中的来源、传递与 fallback（项目存在 i18n 时）；
- 兼容性、迁移与回滚；
- 与风险匹配的验证方法。

实施时：

- 遵循仓库已有架构和错误模型；
- 在边界处验证不可信输入；
- 把授权检查放在真正访问资源的路径上，不只检查上游声明；
- 保护密钥、token、个人数据和日志；
- 数据越过 API、日志、遥测、消息、第三方 SDK 或模型边界前执行最小化和服务端脱敏；
- 对写操作明确事务边界、重复请求和部分失败行为；
- 修改共享契约时同步检查所有生产者与消费者；
- 避免与当前目标无关的重构。

## Backend Reviewer

不要把任务描述、补丁说明或 Builder 的解释当作事实。按以下顺序核查：

1. 读取真实 diff；
2. 读取变更函数的调用方和下游消费者；
3. 检查配置、schema、迁移、序列化和测试；
4. 构造正常、异常、边界和对抗场景；
5. 用测试、日志、运行结果或明确的代码路径证明结论。

前后端同时受影响时，Backend Reviewer 只能关闭 backend 审查单元。不得因后端已修复或后端测试通过而把 frontend、shared-contract/integration 一并标记完成；这些单元必须由各自的代码路径和验证证据独立销账。

涉及契约迁移或批量机械替换时，不能只使用下方通用矩阵；必须同时执行主 skill 指向的 Contract Migration 覆盖账本、双向穷举和测试盲区审计。

### 审查矩阵

只检查适用维度，但不得遗漏高风险路径：

- **逻辑正确性**：分支、返回值、空值、类型转换、状态机；
- **契约兼容性**：字段、状态码、版本、默认值、序列化、旧客户端；
- **数据完整性**：事务、约束、迁移、回滚、部分写入；
- **鉴权与隔离**：身份来源、权限判定、对象归属、租户边界；
- **输入与注入**：SQL、命令、模板、路径、SSRF、不可信反序列化；
- **数据出口与脱敏**：敏感字段分类、响应/导出、日志/trace、第三方 SDK/API、消息、缓存/搜索/向量库及模型请求；
- **凭据链路**：issuer、forwarder、downstream parser、日志和缓存都要检查；
- **并发与幂等**：竞态、重复请求、锁、任务重放、顺序假设；
- **错误与韧性**：超时、重试、取消、熔断、错误映射和可恢复性；
- **本地化链路**：稳定错误码与文案映射、服务端校验消息、邮件/通知 locale、后台任务默认语言、missing key 和 fallback；
- **资源与性能**：连接、文件句柄、内存、无界集合、N+1、热点路径；
- **可观测性与隐私**：指标是否有用，日志是否泄密，错误是否可定位；
- **LLM / Agent**：prompt/context、RAG/memory、模型输入输出、streaming、provider retention、prompt injection、tool/MCP 参数与最终授权；
- **回归面**：调用方、后台任务、CLI、管理端、旧数据和已有测试。

不要为了覆盖矩阵而制造问题。某项未发现问题时，按主 skill 的“未发现问题”格式记录实际检查范围。

命中敏感数据、外部出口、注入面或 LLM/RAG/Agent 时，必须同时执行 [Security / Sensitive Data / LLM Egress Review](security-data-egress.md)。通用矩阵不能替代出口账本、LLM 强制矩阵和 canary 验证。

## 发现与复审

有效发现必须指向真实文件和尽量精确的行号，并说明触发条件、影响和最小修复建议。仅有风格偏好、无法触发的猜测或没有影响说明的意见，不应升级为缺陷。

修复后：

- 重新读取修改后的代码；
- 检查修复是否引入新的兼容性、安全或数据风险；
- 有源码复审证据但尚未进入阶段末验证时标记为 `fixed-unverified`；
- 本阶段审核和必要关闭轮结束后，由 `stage-validation` 集中运行能证明各问题已解决的测试，再分别记录已解决、未解决、接受风险和无法验证的项目。

不得为每个后端问题单独重跑 lint、typecheck、build 或测试。集中验证失败时先汇总同批失败并批量修复，完成对应关闭审查后再重跑失败项和受影响回归；提前只允许主 Skill 定义的阻塞性最小诊断。

是否允许写入严格遵循主 skill 的“默认修复协议”：显式调用 Dark Tribunal 默认进入 Builder 修复与复审闭环，普通 review/audit 默认只读，显式只读要求始终优先。获得写入授权后不再询问用户“是否修复”；只有修复超出范围、需要业务决策、涉及高风险外部写入或与用户现有改动冲突时，才升级给用户。

纯前端改动时将 Backend Builder 和 Backend Reviewer 标记为 `N/A`。前端调用契约变化时，至少执行契约检查，不要求修改无关后端实现。
