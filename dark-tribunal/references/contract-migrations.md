# Contract Migration / Bulk Change Review

错误码、状态码、API/schema、事件、共享类型、配置键、feature flag、路由标识、生成代码或注册表发生变化时，必须使用本参考。批量搜索替换、多文件机械改写也必须使用。

目标不是“又搜了一遍”，而是证明迁移覆盖闭环。

## 1. 先建立覆盖账本

修改或审查前先写账本，不边查边决定范围：

```text
| 类别 | 对象或模式 | 预期集合/数量 | 发现方式 | 状态 | 证据或排除理由 |
| source | 定义、schema、注册表 | ... | ... | unchecked | ... |
| transform | generator、mapper、wrapper | ... | ... | unchecked | ... |
| sink | 调用出口、序列化、UI 分支 | ... | ... | unchecked | ... |
| consumer | 前端、CLI、任务、旧客户端 | ... | ... | unchecked | ... |
| test | 测试与断言 | ... | ... | unchecked | ... |
| docs | 文档、示例、运维配置 | ... | ... | unchecked | ... |
```

状态只能是 `checked`、`excluded`、`blocked` 或 `unchecked`。结束时不得保留未解释的 `unchecked`；`excluded` 必须给出可复核理由。

`test` 类别在审核轮标记 `checked` 只表示测试入口、fixture、断言和盲区已审计，并已进入阶段验证矩阵；实际运行结果必须由审核关闭后的 `stage-validation` 单独记录。

## 2. 双向穷举，不只顺着 diff 看

同时执行两条路径：

1. **source → sink**：从定义、schema 或注册表出发，追踪 generator、mapper、序列化、公开出口和全部消费者，确认每个定义都能到达预期出口。
2. **sink → source**：从写入函数、错误响应、事件发送、配置读取或 UI 分支反向穷举所有调用点，确认每个出口都能映射回合法 source 或明确的兼容分支。

比较两侧数量与集合差异。任何“source 有而 sink 无”“sink 有而 source 无”都必须解释，不能用总测试通过代替。

优先使用 AST、语言服务器、编译器引用或项目索引；文本搜索只能作为基线。动态语言或工具受限时，组合搜索别名、wrapper、接口实现、生成物和运行时注册路径，并披露仍可能漏检的动态行为。

## 3. 穷举调用形态

对每个关键出口（例如 `writeErr`、事件发送器、序列化器、配置读取器）分类登记所有参数来源：

- 字面量或常量；
- 局部变量、字段或成员访问；
- 函数/方法调用，例如 `err.Error()`；
- wrapper、alias、接口或回调转发；
- 字符串拼接、格式化、模板或条件表达式；
- map/lookup、反射、动态键或配置驱动值；
- 生成代码、宏或代码生成器输出；
- 外部系统、操作系统、第三方库或透传 payload。

每一类都要么映射到稳定契约，要么明确走动态/未知值的兼容和降级路径。不要只搜索字面量；不要把“参数类型相同”当作语义一致。

## 4. 审计测试观察边界

在引用测试结果前回答：

- 测试入口和 fixture 来自哪里？
- 断言实际观察了哪个层级和哪些字段？
- 它只覆盖字面量、登记数据或生成物吗？
- wrapper、动态参数、外部错误、旧数据和真实消费者是否绕过了测试？
- 测试 oracle 能否识别错映射、漏映射、重复键和 silent fallback？

测试通过只证明已观察范围内未触发断言，不证明调用形态或影响面完整。针对每个盲区增加人工追踪、静态查询、定向测试或真实运行验证。

## 5. 批量机械改动专项复验

任何多文件替换、生成器更新或自动修复之后，先完成审核侧复验：

1. 逐文件阅读完整 diff，检查误替换、漏替换和越界修改；
2. 检查 imports、类型、符号引用、格式化和死代码；
3. 若存在生成器或派生物，重新生成并检查生成过程幂等、工作树无意外漂移；
4. 重新执行 source ↔ sink 集合对账，确认替换没有创造新孤儿或动态漏口。

审核侧复验、第二轮差异化审查与必要关闭轮完成后，再由 `stage-validation` 一次性执行：

5. 若项目提供对应入口，运行目标语言的编译/类型检查、lint 和定向测试；
6. 若存在可执行行为和回归入口，运行与影响面匹配的回归，而不只运行新增 guard test。

不得在每个替换文件或每个修复点之后重复执行第 5–6 项。集中验证失败时先批量处理同组失败，完成关闭审查后再重跑失败项和受影响回归。

表面确实存在但因环境、权限或依赖无法运行时，标记为 `blocked` 并说明影响；项目不存在该表面时可标记 `excluded`，但要给出文件结构、脚本清单或项目类型等可复核依据。不得把未检查项写成通过。

## 6. 新发现触发扩面，而不是局部打补丁

后续轮次发现新问题，说明之前的覆盖模型有缺口。先把问题归入一种漏检类型：

- 漏了 source；
- 漏了 sink/consumer；
- 漏了调用形态；
- 错信测试覆盖；
- 批量改动引入副作用；
- 文档、生成物或兼容路径漂移。

把新类别补入账本，然后重查该等价类的全部位置。例如发现一个 `err.Error()`，应审查所有非字面量参数，而不是只修这一个调用点。

第二次审查必须改变搜索策略或扩大证据面；重复同一搜索并得到相同结果不构成有效第二轮。第二轮若发现动态调用形态、遗漏出口或批量改动副作用，先更新账本并扩查同类全部位置；第二轮只要修改任何任务产物或工作区文件，修复后就追加关闭轮。

## 7. 关闭条件

只有同时满足以下条件，才可声明契约迁移完整：

- source、transform、sink、consumer、test、docs 均已销账；
- 所有调用形态已分类，动态值有明确策略；
- 定义侧与出口侧的集合/数量差异均已解释；
- 测试盲区已列出并由其他证据覆盖或作为残余风险披露；
- 批量改动经过完整 diff 复验，且所有适用的编译/类型、生成和回归表面已 `checked`，不适用项已证据化 `excluded`；
- 新发现触发的同类扩面检查已经完成；
- 至少两轮审查采用了不同方法；若第二轮发现需要继续处理的问题，关闭轮已经完成。

输出覆盖摘要，而不是只写“全量搜索无遗漏”。
