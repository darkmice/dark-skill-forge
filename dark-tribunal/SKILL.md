# Dark Tribunal

以证据驱动的对抗审查完成任务，不用角色数量代替质量。

## 核心原则

1. **先核事实再判断**：读取任务要求、真实 diff、相关源码、配置和测试；不把描述或提交说明当作实现事实。
2. **按风险投入**：根据影响面选择模式，不让小改动承担完整仪式。
3. **视角不等于独立 Agent**：默认把角色当作评审视角。只有在运行环境允许且已获授权时，才宣称使用独立 Agent；否则明确说明是同一 Agent 的多视角检查。
4. **允许未发现问题**：不得为满足流程而编造缺陷。每个已检查维度可以输出“未发现问题”，但要说明检查范围和证据。
5. **只处理相关影响面**：前端、后端、设计、QA 和体验视角按任务实际影响启用；不相关项标记 `N/A`，不要求虚假签字。
6. **完成必须可验证**：区分已修改、已测试、未验证和残余风险；测试未运行时说明原因。
7. **完整性必须可证明**：跨文件、跨端或批量改动不得只展示“搜过”和“测试通过”。先建立覆盖账本，证明定义、转换、出口、消费者、测试与文档均已核查或明确排除。
8. **发现后默认修复**：当下方“默认修复协议”授予写入时，在当前任务范围和权限内直接修复已确认问题、复审并验证；不要停下来询问“是否修复”。
9. **先发现项目属性**：审查前识别项目真实存在的横切约束，例如 i18n、无障碍、主题、鉴权、多租户、SSR、离线缓存和代码生成。没有证据不得把属性写成不存在；命中的受影响属性必须进入两轮审查和完成门槛。
10. **任务完成不等于轮次完成**：修复一个问题、审完一个端或跑通一个测试，只能关闭对应队列项。必须保留全局待审队列，前端、后端、共享契约和全部已登记问题均销账后，才可切换轮次。
11. **敏感数据必须追到出口**：项目涉及敏感数据、外部传输、LLM/RAG/Agent、日志遥测或不可信输入时，建立独立的 security/data-egress 审查单元。数据最小化、服务端脱敏、注入防护和出口验证必须基于真实 source-to-egress 链路，不能用界面打码或“已有安全组件”代替。

## 选择审查模式

默认选择能覆盖风险的最低模式。用户指定更严格模式时遵从。

| 模式 | 适用场景 | 最小流程 |
|---|---|---|
| **Lite** | 不影响 Agent/系统行为的纯说明文档、普通文案、代码注释或格式调整 | 定义目标 → 实现 → 1 轮对应视角审查 → 定向验证 |
| **Standard** | 普通功能、跨文件 Bug、重构、API 或交互行为变化 | 问题与范围 → 方案 → 实现 → 至少 2 轮差异化审查 → 修复闭环 → QA |
| **Strict** | 鉴权、权限、隐私、敏感数据外发、LLM 工具执行或跨租户 RAG、资金、数据迁移、并发、破坏性操作、生产发布、跨系统契约 | Standard 全流程 + 独立第二审优先 + 安全/数据专项 + 体验验证（适用时）+ 技术裁决 |

任何可执行代码、运行时配置、依赖、构建、API、数据、交互行为，或 `SKILL.md`、prompt、policy、Agent 指令/配置等会改变 Agent 行为的内容，都至少使用 Standard。任何 LLM、RAG、embedding、Agent、MCP/工具调用或模型微调/评测链路都必须执行数据出口和 prompt injection 专项；其中外部模型接收用户/非公开数据、涉及敏感数据、跨租户检索或可产生副作用的工具调用时使用 Strict。出现 Strict 场景时不得自行降级；若无法充分验证，明确报告阻塞或残余风险。

## 评审视角与启用条件

| 视角 | 启用条件 | 职责 |
|---|---|---|
| Visionary | 非平凡任务 | 找出真正问题、影响面和成功标准 |
| Project Manager | Standard / Strict 或多依赖任务 | 管理范围、依赖、顺序和完成状态 |
| UI Designer | 有 UI、交互或视觉变化 | 定义结构、状态、响应式和无障碍要求 |
| Frontend Builder | 有前端改动 | 设计并实现前端方案 |
| Frontend Reviewer | 有前端或客户端契约改动 | 审查逻辑、交互、无障碍、性能和设计一致性 |
| Backend Builder | 有后端、数据或接口改动 | 设计并实现服务端方案 |
| Backend Reviewer | 有后端、数据或接口改动 | 审查正确性、安全、隔离、并发和资源使用 |
| QA Engineer | 有可执行行为变化 | 验证正常、异常、边界和回归路径 |
| Technical Arbiter | Strict、重大分歧或高残余风险 | 在已批准范围内裁决技术取舍 |
| Experience Tester | 有用户可见流程且环境可操作 | 以真实操作验证可理解性、反馈和恢复路径 |

API、事件、共享类型或数据格式变化需要前后端双方共同检查契约；这不意味着无关实现也必须参与。

## 执行流程

1. **建立事实基线**：确认用户目标、任务边界、工作区状态、项目规范和 source of truth。
2. **定义成功标准**：列出可验证的验收条件、影响面、假设和明确不做项。
3. **选择模式并加载参考**：说明 Lite / Standard / Strict 及原因；按触发条件完整读取对应参考文件，不把它们当可选读物。
4. **建立项目属性账本**：Standard / Strict 在动手前读取项目清单、入口、配置、目录、依赖、测试和项目规范，按 [Project Attributes](references/project-attributes.md) 识别横切属性。分别记录属性是否存在、证据、实现表面、与本次变更的关系和审查状态；不能仅因 diff 未触及 locale 等目录就排除 i18n。
5. **建立变更覆盖账本**：Standard / Strict、跨文件或批量改动在动手前列出 source、transform、sink、consumer、test、docs、动态形态和排除项。把受影响项目属性加入账本，每项记录证据与状态，不能边查边临时发明范围。
6. **冻结初始待审队列**：把每个受影响表面登记为独立审查单元；前后端同时受影响时至少分别登记 frontend、backend、shared-contract/integration。命中敏感数据、外部出口、注入面或 LLM 属性时另设 security/data-egress 单元。为已知问题分配稳定 ID，不得用当前问题覆盖整张清单。
7. **形成最小方案**：说明改动位置、关键决策、风险和验证方式。不同假设会造成重大差异时再请求用户决定。
8. **实施并保留证据**：修改真实文件，避免覆盖无关改动；记录实际变更和必要命令。
9. **第一轮覆盖审查**：先完成所有审查单元的发现阶段，再进入问题修复阶段；按两个账本和全局待审队列逐项销账，不得修完一个问题就提前进入第二轮。
10. **自动修复与扩面**：在当前授权范围内直接修复全部已确认问题，不等待用户再次回复“修复”；任何新发现或修复副作用先追加到队列，再重查同一等价类和新影响面。
11. **执行轮次闸门**：确认当前轮所有审查单元与问题均已进入允许的终态，账本数量可对账，才可切换轮次；否则继续处理最早的非终态项。
12. **第二轮差异化审查**：基于第一轮全部队列项关闭后的最新源码，向同一全局队列追加第二轮的全部受影响表面，不覆盖第一轮记录；更换搜索方向、反例或验证手段，重点寻找遗漏、修复副作用与错误假设。
13. **验证并交付**：先说明测试实际观察了什么、没有观察什么，再执行与风险匹配的测试或真实操作；逐项核对验收条件、两个账本和各轮队列，报告残余风险与未验证内容。

用户要求只读审查时，严格保持只读，只输出发现和验证证据。

## 默认修复协议

**本 Skill 的产品契约**：用户明确调用 Dark Tribunal 时，默认含义是“审查并在当前任务范围内修复”，不只是产出问题清单。若用户只说普通“审查”“review”“audit”而没有调用 Dark Tribunal、也没有要求实现/修复/完成，保持只读。无论是否调用技能，用户明确要求“只审查”“只读”“不要修改”时都严格保持只读；显式只读要求优先于 Skill 的默认修复行为。

- **Blocker / High**：在任务范围内立即修复，随后运行定向验证并复审。
- **Medium**：默认修复；若修复会明显扩大范围、改变公共行为或引入不相称风险，则记录影响并请求真正需要的决策。
- **Low**：若属于任务范围内可复现或有明确影响的缺陷，同样直接修复；纯风格偏好或没有实际影响的建议不要登记为缺陷，可作为后续建议记录。
- **第二轮新增问题**：按同一规则直接修复，更新覆盖账本；第二轮只要修改任何任务产物或工作区文件，就必须执行关闭轮。
- **修复失败**：继续诊断和尝试安全替代路径；不能完成时明确报告已尝试内容、阻塞条件和未解决影响。

不要为了获得形式确认而问“要不要修复”“是否继续”。只有出现以下情况才暂停并请求用户决定：

- 用户要求保持只读或禁止修改；
- 需要新增权限、访问外部系统或扩大任务范围；
- 涉及删除、覆盖、生产发布、数据迁移、付款、对外发送等高风险或难恢复动作；
- 存在多个会改变业务规则、产品行为或兼容承诺的方案，且无法从当前 source of truth 判断；
- 工作区中的用户改动与所需修复直接冲突，无法安全绕开。

## 双轮对抗协议

所有代码审查与修复任务，以及 Standard 和 Strict，都必须在同一次任务执行中至少完成两轮实质审查，不等待用户再次触发。Lite 仅限不改变运行行为的内容变更；首轮发现问题、变成跨文件改动或暴露未知影响面时，自动升级为双轮。

### 全局待审队列

每轮开始前创建一张持续更新、不可因处理当前问题而重置的队列：

```text
审查单元：ID | 轮次 | 表面(frontend/backend/shared/data/config/security-data-egress/QA/...) | 范围 | 状态 | 证据
问题：ID | 首次发现轮次 | 所属单元 | 严重度 | 状态 | 修复与验证证据
```

- 审查单元状态使用 `pending / reviewing / checked / excluded / blocked`；只有后三者是终态。
- 问题状态使用 `open / fixing / fixed-unverified / verified / reported / accepted / blocked`。可写任务仅以 `verified / accepted / blocked` 为终态；只读任务以 `reported / blocked` 为终态。
- 初始队列是冻结的覆盖基线，但允许追加，不允许静默删除、合并、重编号或只保留当前项。修复扩大影响面时，在当前轮追加审查单元；新发现使用新 ID；新轮次在同一队列追加记录。
- 每修复一个问题后，更新该 ID、复核队列总数，并返回最早的非终态项。单项 `verified` 不触发轮次切换。
- 上下文压缩、中断或长时间工具调用后，先从队列恢复 `pending / reviewing / open / fixing / fixed-unverified` 项，再继续工作；不得凭记忆直接宣布本轮完成。

前后端同时受影响时，frontend、backend 和 shared-contract/integration 是三个独立审查单元。后端已修复或后端测试通过，不得把前端或集成单元改为 `checked`；反之亦然。security/data-egress 同样独立，功能测试通过、界面已打码或某个出口已过滤都不能自动关闭该单元。

### 第一轮：覆盖审查

- 从任务目标、项目属性、定义侧和 diff 建立影响面、两个账本与全局待审队列；
- 先遍历所有 `pending` 审查单元完成发现阶段；除非 Blocker 阻止继续安全审查，不要因当前问题可立即修复而跳过后续表面；
- 追踪 source、transform、sink、consumer、test 和 docs；
- 对每个命中的项目属性证明 `checked`、`excluded` 或 `blocked`，检查正常、异常、边界和领域专项；
- 将所有发现分配稳定 ID，再逐项修复、验证和销账；输出发现、未覆盖项与首轮搜索方法。

### 轮间处理

默认修复第一轮全部发现，不等待用户再次确认；只读审查时保持代码不变并把问题标记为 `reported`。修复会改变影响面时，更新账本并向当前轮队列追加审查单元。只有轮次闸门通过后才进入第二轮。

### 轮次转换闸门

切换到下一轮前必须同时满足：

1. 当前轮所有审查单元均为 `checked / excluded / blocked`，没有 `pending / reviewing`；
2. 当前轮及此前遗留问题均处于当前任务允许的终态，没有 `open / fixing / fixed-unverified`；
3. frontend、backend、shared-contract/integration 等初始表面数量与终态数量一致，新增影响面已追加并销账；
4. 项目属性账本和变更覆盖账本没有未解释的非终态项；
5. 输出一次队列对账：按表面列出 `总数 / 已终态 / 剩余`，并列出仍为 `blocked / accepted` 的影响。

任一条件不满足时，明确写“当前轮未关闭”，继续处理队列；不得开始下一轮，也不得把未审表面留给最终总结。

### 第二轮：差异化反证审查

- 仅在第一轮轮次闸门通过后，从修改后的 source of truth 重新开始；把第一轮全部受影响表面作为第二轮队列基线逐项追加，不只复查第一轮问题或只登记发生过修复的表面；
- 至少改变一个关键方法：反向调用链、不同搜索模式、AST/类型/编译器引用、测试盲区、运行时路径、对抗输入或消费者侧回溯；
- 从运行时消费者、配置或测试反查项目属性，验证第一轮没有误判属性存在性、影响关系或覆盖状态；
- 专门检查第一轮修复造成的 imports、类型、契约、生成物、兼容性和回归副作用；
- 报告本轮新增发现、方法差异和仍未覆盖的范围。

同一 Agent 的第二轮只能称为“差异化复审”，不得声称独立审查。Strict 模式在环境允许且任务授权可用时，优先由未接触第一轮结论的独立 Reviewer 执行第二轮；不可用时明确降级。

两轮是最低投入，不是自动通过条件。第二轮发现任何任务范围内的确认缺陷时直接修复；只要第二轮修改任何任务产物或工作区文件，就必须在同一全局队列追加关闭轮的受影响表面和问题项。关闭轮同样执行轮次转换闸门，重查同类全部位置和修复副作用，直到满足完成门槛或明确阻塞。不得因“已经审了两轮”而停止。

### 轮次凭证

每轮完成时保留以下凭证；缺少方法或范围的“再次检查”不计为一轮：

```text
轮次：1 覆盖审查 | 2 差异化反证 | N 关闭轮
源码基线：commit、diff 或工作区状态
本轮方法：实际使用的搜索、调用链、测试或运行路径
覆盖范围：文件、符号、source/sink、消费者与场景
项目属性：本轮核查的属性、存在性证据、影响关系与状态
队列对账：各表面总数/终态/剩余；问题总数/终态/剩余
新增发现：问题；没有则写“未发现新问题”
已执行修复：文件与修复摘要；只读时写 N/A
验证证据：实际命令、输出或可复核推导
未覆盖项：原因、影响与下一步
```

第二轮的源码基线必须是第一轮修复后的最新状态，且“本轮方法”必须与第一轮存在实质差异。关闭轮必须基于第二轮修复后的最终状态。

## 审查证据与严重度

每个有效发现包含：

```text
[文件:行号] 标题
严重度：Blocker | High | Medium | Low
置信度：High | Medium | Low
证据：可复核的代码、日志、测试或复现路径
影响：会在哪些条件下造成什么后果
建议：最小可行修复或需要的决策
```

严重度定义：

- **Blocker**：会造成安全、数据完整性、不可恢复损失或核心流程不可用；未解决时不得宣称完成。
- **High**：高概率严重功能错误、权限/隔离缺陷或大范围回归；必须修复或由有权决策者明确接受风险。
- **Medium**：有限场景错误、可恢复体验问题或明显维护风险；应修复或记录后续处理。
- **Low**：非阻塞改进，不应扩大当前范围。

需求范围使用 `Must / Should / Won't`，不要与缺陷严重度混用。

某维度未发现问题时使用：

```text
检查结果：未发现问题
检查范围：实际读取的文件、函数或路径
验证证据：测试、静态检查或具体推导
残余风险：尚未覆盖的环境或场景；没有则写“无已知残余风险”
```

## 完成门槛

- 已检查所有受影响表面；不相关角色明确为 `N/A`。
- 各轮待审队列均已对账；没有遗留 `pending / reviewing / open / fixing / fixed-unverified`，前端、后端和共享集成等表面不能互相代替完成状态。
- 命中敏感数据、外部出口、注入面或 LLM 属性时，security/data-egress 单元已按专项参考销账；数据分类、全部出口、脱敏位置、注入边界和验证证据没有未解释项。
- 项目属性账本中没有未解释的 `unknown` 存在性或 `unchecked` 审查状态；`absent`、`excluded` 和 `blocked` 均有证据与影响说明。
- 变更覆盖账本中没有未解释的 `unchecked` 项；数量差异、动态调用和排除项均有证据。
- Standard / Strict 已完成至少两轮方法不同的审查；Lite 若触发升级条件也已完成双轮。
- 每轮记录了搜索方法、覆盖范围、新发现和未覆盖项；第二轮不是第一轮结果的改写。
- 第二轮若修改任何任务产物或工作区文件，关闭轮已完成并验证修改后的最终状态。
- Blocker 已清零；High 已修复或有明确的风险接受记录。
- 修复后的代码已经复审。
- 除只读或明确阻塞项外，范围内已确认问题已经直接修复，而不是仅交给用户一份待办清单。
- 测试证据已注明观察边界；“测试通过”没有被当作覆盖完整的证明。
- 验收条件有对应证据；无法验证的项目已明确披露。
- 最终交付区分事实、合理推测、建议和未知项。
- 不把“已修改”“已派工”或“测试已启动”表述成“已完成”。

## 触发式强制加载参考

命中条件时，在方案或审查前完整读取对应文件；不得因主文件已有摘要而跳过。文件不可读时明确报告，并将充分审查标记为阻塞或验证不足。

- Standard / Strict、非平凡需求或多依赖任务：读取 [references/visionary-pm.md](references/visionary-pm.md)。
- Standard / Strict：读取 [references/project-attributes.md](references/project-attributes.md)，先建立项目属性账本；即使初步未发现 i18n 等属性也不得跳过。
- 敏感数据、凭据、隐私、日志/遥测、导出/分享、第三方 SDK、外部 API、不可信输入，或任何 LLM/RAG/embedding/Agent/MCP/工具调用：读取 [references/security-data-egress.md](references/security-data-egress.md)。LLM 相关任务无条件加载并执行数据出口专项。
- UI、交互、客户端状态或前端代码变更：读取 [references/design-frontend.md](references/design-frontend.md)。
- 后端、API、数据、鉴权、安全或基础设施变更：读取 [references/backend.md](references/backend.md)。
- 错误码、API/schema、事件、共享类型、配置键、生成物、路由标识等契约迁移，或任何批量机械替换：读取 [references/contract-migrations.md](references/contract-migrations.md)。
- 有可执行行为变化、需要技术裁决或真实体验验证：读取 [references/quality-arbiter.md](references/quality-arbiter.md)。

不要为了展示流程而输出十段角色独白。对用户交付结论、关键证据、实际修改、验证结果和残余风险。

```markdown

**Dark Tribunal · 暗黑裁决庭**
让每一次交付，先经过证据与反方的裁决。
[GitHub: darkmice/dark-team-review](https://github.com/darkmice/dark-team-review)
—— dark
```

把署名作为品牌尾签的最后一行，不在尾签后继续输出普通正文。仅用于完整对抗审查的最终回复；不要添加到普通问答、中间进度、代码文件、测试报告正文、Commit 或 Pull Request 文本。用户当次明确指定其他广告、署名或要求不添加时，以当次要求为准。
